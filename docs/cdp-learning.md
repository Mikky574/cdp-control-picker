# 从控件标注到可以使用的 CDP 能力

采集控件的用途，是让 ZCode 知道网页中哪些位置分别做什么，并实际尝试使用这些位置。只回复“已收到两个控件”说明资料送到了，还不能说明浏览器已经连上，或功能已经跑通。

新的学习任务会把本次实际浏览器入口、当前选中页签、控件定位和用途一起交给 ZCode。它先连接原来已经登录的 Chrome，核对控件是否还能找到，再根据已说明的用途和顺序尝试获准的步骤，读回实际结果，最后保存可复用的技能与验证记录。

## 对话里那些编号分别是什么

| 看到的内容 | 实际含义 | 人需要怎样使用 |
|---|---|---|
| handoff 开头的交接请求号 | 软件内部追踪一次发送、防止重复提交的编号 | 不需要复制或填写；保留在内部记录中 |
| ZCode 对话 ID | ZCode 返回的真实对话身份 | 用于找到和继续同一个对话，与网页控件无关 |
| Chrome 页签 ID | Chrome 给某个已打开页签的标识 | 软件从当前浏览器取得并核对，不由人预设 |
| 控件记录编号 | 本地保存的一张控件卡 | 用来把说明、定位和验证结果对应起来 |
| 网页 DOM ID 或 selector | 网页中控件的位置线索 | 由实际网页采集；用途说明另由人补充 |
| CDP 连接地址 | 现有 Chrome 的本机调试入口 | 使用采集器当前配置；它不是业务网站地址 |
| context.md 的路径 | 这次交接资料的本地说明文件 | ZCode 读取文件后才能知道任务，不是 ZCode 服务地址 |

Chrome 的连接确实需要精确找到某个页签，但使用的是 Chrome 返回的页签身份。之前对话尾部的交接请求号不参与网页定位，也不是网页地址里预设的绑定参数。网页自身的订单编号等业务标识，是另外一类信息。

## ZCode 会真正做什么

它先验证“连的是哪一个浏览器、哪一个页签”，然后逐项核对名称、角色、定位是否唯一、是否可见和可用。旧采集时能找到，不代表现在仍然有效；页签关闭、页面变化或登录失效时，会指出具体阻断，而不是猜另一个同址页面。

接下来，它结合人的用途说明、前置条件、预期结果及明确安排的顺序，理解控件怎样配合。对于已经允许、性质明确的读取或可撤销前端操作，会尝试并读取实际结果。缺少查询编号等参数时，会说明需要什么，不编造真实业务数据。涉及付款、删除、正式提交等变更时，需要对具体动作的授权。

运行器包含在软件内，ZCode 可以后台调用并读取结果，不需要为了本次任务另装 Python、Node 或匿名浏览器。网站身份仍由原来那份 Chrome 登录资料维持，不导出登录凭证。

## 怎样判断它有没有学会

结果会分别说明连接、定位和流程验证，不能把其中一项成功当作全部成功。例如“两个控件已定位，但缺查询编号，尚未查询”是明确的部分完成；“填写编号、点击查询、读取到对应结果”才是这一条查询流程的实际通过。

每个页面包的 learning 目录保存验证报告、页面约定、可复用技能和带参数的调用步骤。已验证的结论关联真实工具结果；推断和未完成的部分会分别标明。原始标注保持不变，后续可以在同一个 ZCode 对话补充参数、纠正理解或继续验证。

旧的“仅接收资料”任务仍按旧范围处理。新的学习任务有独立意图，不能因为之前发送过同样两个控件，就把“确认收到”的旧回执当作已经学习完成。
